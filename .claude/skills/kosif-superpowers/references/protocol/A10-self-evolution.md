### -1.10 بروتوكول التطور الذاتي عند تعديل SEE أو Superpowers

عند تطوير هذا البروتوكول/مهاراته، التزم: `(1) baseline/version + SHA-256؛ (2) فرضية تحسن واحدة قابلة للقياس؛ (3) candidate قابل للتراجع؛ (4) مراجعة مستقلة للتغيير المعماري؛ (5) اختبارات shadow للتشغيل وعدم التشغيل والتصادم والفشل؛ (6) فحص JSON والإصدارات وRegistry/Fabric وNo-secrets؛ (7) مقارنة baseline/candidate؛ (8) رفض أي HARD_FAIL؛ (9) نشر محمي بالمعرف/الإصدار الحي إن صُرّح؛ (10) read-back للبنية المنشورة؛ (11) إضافة سجل إصلاح غير قابل لمحو القديم`.

**فاصل مهم:** كتابة Markdown محسّن وتسليمه **ليست تحديثًا للإضافة المنشورة** وليست اختبارًا ناجحًا لسكربتات مستودع غير متاح. سجّل حالتين منفصلتين: `DOCUMENT_READY` و`RUNTIME_INTEGRATION_VERIFIED`، ولا تجعل الأولى دليلًا للثانية. إن اختلفت بيانات الإصدار مع الحزمة الفعلية: `REGISTRY_VERSION_DRIFT`، وإن غاب ملف Runbook أو بقي فهرس الجهاز قديمًا، اذكر عدم اليقين بدل ادعاء النشر.

### -1.34 قاعدة الحد الأعلى: فكّر بأقصى جودة ونفّذ بأصغر سطح مأذون

الهدف ليس محاكاة «قدرة خارقة» بالوعود، بل اختيار أفضل توليفة مدعومة بالبرهان ثم تحويلها إلى أثر. يحظر هذا الفصل تقديم البروشورات والوصف كأدوات، الإصرار على أعطال الجسور، اختلاق أرقام نماذج أو موافقات، أو إعادة إنشاء KOSIF SEE بوابة ثانية. توسّع في الحجة والاختبار حيث يوجد أثر، واختصر القراءة والأسئلة عند اليقين. أثبت التحسّن بالمقارنة، وتوقف عندما يغلب خطره أو تكلفته فائدته.

### جسر SEE — المرحلة 10 (منقول من النواة)

**جسر التطوير الذاتي SEE:** أي تعديل لمسار الحزم الفكرية أو Registry/Fabric/Full Pro يخضع إلى `SELF_EVOLUTION_PROTOCOL`: baseline، فرضية، candidate، shadow tests، HARD_FAIL، مقارنة، إذن نشر، read-back، وسجل إصلاح غير قابل لمحو القديم. تحسين هذا الملف محليًا لا يعني أن الإضافة المنشورة أو مستودع GitHub قد تغير. (v5.3: `SELF_EVOLUTION_PROTOCOL` شرطي: يُقرأ حين تكون حزمة SEE مثبتة؛ في kosif-tool تكفي الخطوات نفسها مع الأمرين أعلاه.)
